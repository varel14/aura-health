# Aura Health — API backend

Node.js + Express + PostgreSQL backend for the Aura Health mobile app. It serves
every app flow: auth (patient & doctor), catalog, appointments booking & payment,
chat consultations, AI-style consultation summaries, prescriptions, pharmacy cart
/ checkout / delivery tracking, wallet-style payment history, notifications,
symptom triage and the doctor workspace.

## Setup

```bash
npm install
cp .env.example .env            # adjust PGUSER/PGHOST if needed
npm run db:reset                # drop + recreate schema + seed from mock data
npm start                       # http://localhost:4001  (npm run dev = watch mode)
```

### AI (Groq or GLM)

The symptom analysis and the consultation summaries are generated by an
OpenAI-compatible provider: **Groq** (`GROQ_MODEL`, default
`llama-3.3-70b-versatile`) or **GLM/Zhipu** (`GLM_MODEL`, default `glm-4.6`).
`AI_PROVIDER` selects the provider (`groq` by default); set the matching
`GROQ_API_KEY` or `GLM_API_KEY` in `.env` to enable it. Without a key (or if
the API fails/times out) both flows transparently fall back to the local
rule-based engine.

What the AI produces and who may see it:
- **Patient**: an orientation message + a priority (`faible`/`modérée`/`élevée`),
  and a non-diagnostic compte-rendu. Never a diagnosis.
- **Doctor**: the clinical diagnostic blocks (symptom synthesis, diagnostic
  hypotheses, red flags, anamnesis questions; summary hypothesis/differentials).
  These are stored with the record and only ever serialized into doctor-session
  payloads (`GET /api/doctor/symptom-preps`, doctor-scope summary reads).
  Red-flag inputs (chest pain, dyspnea, severe intensity…) always force the
  emergency orientation server-side, whatever the model answers.

The seeder imports the same mock dataset the mobile app ships with
(`mobile/src/data`, vendored under `src/seed/mock`), so the API returns exactly
what the app's screens expect, with fresh relative dates.

## API surface

### Auth — `/api/auth`
- `POST /register` — patient onboarding (firstName, lastName, email, phone, sex, birthDate, city, pin)
- `POST /register-doctor` — public doctor onboarding (firstName, lastName, email, phone,
  specialty, pin, hospitalId?, experienceYears?, fee?, bio?). The doctor profile is
  created `pending`: invisible in the catalog, workspace locked, until an admin activates it
- `POST /login` — `{phone, pin}`
- `POST /demo` — `{role: 'patient'|'doctor'|'pharmacist'|'delivery'|'admin'}` one-tap demo sign-in
- `GET /me` · `POST /logout`
- `POST /forgot-password` → demo code `000000` · `POST /reset-password`

### Catalog — `/api` (public)
- `GET /specialties`
- `GET /doctors` (`?query&specialty&availableToday&videoOnly&hospitalId`) · `GET /doctors/:id`
- `GET /doctors/:id/slots?date=` — template slots minus real bookings
- `GET /hospitals` (`?query&city&specialty`) · `GET /hospitals/:id` (+doctors)
- `GET /pharmacies` (`?query&city&onDutyOnly&deliveryOnly&medicationId`) · `GET /pharmacies/:id` (+stock)
- `GET /medications` (`?query&pharmacyId&otcOnly&category`) · `GET /medications/:id` (+pharmacies)

### Patient — `/api/patient` (role patient)
- `GET /me` — profile + medical record (allergies, conditions, treatments, vaccines, exam results)
- `PATCH /me` — editable fields + `emergencyContact`
- `GET|POST /documents`

### Appointments — `/api/appointments`
- `POST /` — book `{doctorId, type: video|chat|in-person, date, time, motif, symptoms[]}`; 409 on slot clash; a `chat` booking auto-opens its message thread
- `GET /` · `GET /:id` — scoped to the caller's role
- `POST /:id/cancel` · `POST /:id/reschedule {date, time}`
- `POST /:id/complete {notes?}` — doctor only

### Payments — `/api/payments` (role patient)
- `GET /` · `GET /:id`
- `POST / {category: consultation|order|medkit, relatedId?, method: mtn_momo|orange_money|card}`
  Simulated gateway. Side effects: consultation → appointment `paid`; order →
  status `prête`/`en livraison` + cart cleared; both → notification.

### Consultations — `/api/consultations`
- `GET /threads` · `GET /threads/:id` · `POST /threads/:id/messages` (sender derived from role) · `POST /threads/:id/end`
- `POST /threads/:id/end` — closing a messaging thread also triggers, in the
  background and exactly once per appointment, the AI compte-rendu built from
  the **full chat transcript**; both parties receive a `chat:summary` socket
  push (ids only — clients re-read via the API for role-filtered fields) and
  the patient a notification. The manual generation below remains available as
  an idempotent fallback.
- `POST /summaries {appointmentId}` — generates the post-consultation compte-rendu
  via the AI provider (rule-based French template as fallback), grounded in the
  appointment data **and the chat transcript**: summary + prescription when a
  treatment applies + document + notification. Requires the appointment to be
  completed or its chat thread ended. The AI diagnostic block is included
  only in doctor-session reads. Idempotent per appointment (exactly one
  summary; concurrent triggers resolve to the same row).
- `GET /summaries` (`?appointmentId=`) · `GET /summaries/:id`

### Prescriptions — `/api/prescriptions`
- `GET /` · `GET /:id`
- `POST /` — doctor issues `{patientId, lines[], instructions?}` (code `RX-xxxx`, 3-month expiry)
- `POST /import` — patient imports a paper prescription (+document +notification)

### Pharmacy — `/api/pharmacy` (role patient)
- Cart: `GET /cart` · `POST /cart/items {medicationId, quantity}` (merge, max 10) ·
  `PATCH /cart/items/:medicationId {quantity}` · `DELETE /cart/items/:medicationId` · `DELETE /cart`
- `POST /orders` — checkout `{pharmacyId, mode: delivery|pickup, address?, prescriptionId?}`;
  422 if an Rx item lacks a valid (active, unexpired) prescription; delivery adds 1 000 FCFA;
  creates an unpaid `en attente` order
- `GET /orders` · `GET /orders/:id`
- `POST /orders/:id/advance {status?}` — lifecycle `en attente → confirmée → prête →
  (en livraison →) livrée`, with `annulée` (auto-refund when paid)
- `GET|POST /cart` mirrors the mobile cart cap of 10 units per line

### Notifications — `/api/notifications` (role patient)
`GET /` · `GET /unread-count` · `POST /:id/read` · `POST /read-all`

### Symptoms — `/api/symptoms` (role patient)
- `POST /analyze {symptoms[], duration, intensity, evolution, details?}` — Groq AI
  triage: patient-safe orientation + priority (`faible`/`modérée`/`élevée`), AI
  diagnostic stored for the physician only; falls back to rule-based triage
  (red flags → urgences, enforced even when the AI is active)
- `GET /preps` · `POST /preps/:id/send`

### Doctor workspace — `/api/doctor` (role doctor, profile activated)
`GET /patients` · `GET /patients/:id` · `GET /agenda?date=` (today by default) ·
`GET /symptom-preps?patientId=` — patients' symptom analyses **with the AI
diagnostic** (the only surface that exposes it)

### Admin — `/api/admin` (role admin)
- `GET /overview` — counts: doctors by activation status, hospitals, pharmacies, pending applications
- `GET /doctors?status=pending|active|rejected` — validation queue (with account phone/email, hospital, timestamps)
- `GET /doctors/:id`
- `POST /doctors/:id/activate` — pending|rejected → active (profile becomes visible/bookable, workspace unlocked)
- `POST /doctors/:id/reject {reason}` — pending|active → rejected; the doctor's sessions are revoked
- `GET /hospitals` — basic info + active doctor count
- `GET /pharmacies` — basic info + medication count + open order count
- `GET /applications?status=` — the `POST /api/professionals/apply` submissions

Activation gating: only `active` doctors appear in the public catalog
(`GET /api/doctors`, hospital detail), can be booked (`POST /api/appointments`),
use the doctor workspace (`/api/doctor/*`) or issue prescriptions.

### Misc
- `GET /api/health`
- `POST /api/professionals/apply` — public hospital/pharmacy onboarding form

### Pharmacist workspace — `/api/pharmacist` (role pharmacist, pharmacy-scoped)
End-to-end medication management + order handling (mobile: the `(pharmacy)` tabs).

Medications (per-pharmacy stock over the shared catalog, table `pharmacy_medications`):
- `GET /medications?q=` — the pharmacy's stocked references (`stock`, `lowStockThreshold`, `lowStock`)
- `POST /medications` — `{name, form, dosage, lab?, category?, description?, requiresPrescription, unitPrice, stock?}`
  creates the catalog entry and stocks it (keeps the `pharmacy_ids`/`medication_ids` JSONB links in sync)
- `PATCH /medications/:id` — partial edit of the details and/or `stock`
- `DELETE /medications/:id` — removes the reference from the pharmacy (catalog entry kept)

Couriers:
- `GET /couriers` — the pharmacy's team with `activeDeliveries` load
- `PATCH /couriers/:id {active}` — activate / pause a courier

Orders:
- `GET /orders` — queue, most urgent first
- `GET /orders/:id` — full order + `events[]` progression timeline (`order_events`)
- `POST /orders/:id/validate` — `en attente → confirmée` (409 if not pending, 422 if unpaid)
- `POST /orders/:id/reject {reason}` — → `annulée` (+ refund when paid)
- `POST /orders/:id/assign {courierId}` — assign or replace the courier of a
  delivery order while `confirmée`/`prête` (kept by the subsequent `/ready`)
- `POST /orders/:id/ready` — `confirmée → prête`; keeps a pre-assigned courier, else
  auto-assigns the least-loaded one
- `POST /orders/:id/handover {code}` — pickup handover, customer code required (`prête → livrée`)

### Courier workspace — `/api/delivery` (role delivery, courier-scoped)
- `GET /orders` — run sheet (to collect, in progress, history)
- `POST /orders/:id/pickup` — `prête → en livraison`
- `POST /orders/:id/deliver {code}` — customer code required (`en livraison → livrée`)

Order lifecycle notes:
- Every transition (creation, validation, preparation, assignment, pickup,
  delivery, cancellation) appends an `order_events` row; `GET /api/pharmacist/orders/:id`
  returns it as the order's progression timeline.
- Dispensing (counter handover or delivery) decrements the pharmacy's
  `pharmacy_medications.stock` (floored at 0).
- Orders carry a hashed 6-digit handover code; customers can regenerate it via `POST /api/pharmacy/orders/:id/code`.

The patient-facing contract stays authoritative: checkout returns the order
object, and paying it advances a pickup order to « prête » / a delivery order to
« en livraison » exactly like the mobile checkout's success step.

## Design notes

- **Mapping layer**: SQL rows are snake_case; `src/mappers.ts` is the single place
  that reshapes them into the mobile app's camelCase types, so the frontend types
  in `mobile/src/models/types.ts` remain the contract.
- **Nested data** (prescription lines, order items, symptom lists, medical record
  sections) is stored as JSONB — it is read/written as a unit by the app and never
  queried relationally.
- **State machines** enforced server-side: appointment
  (`confirmed/pending/completed/cancelled`), order lifecycle with refund on
  cancellation, prescription validity (`active`/`expired` from dates).
- **Notifications** are the side-effect channel: booking, payment, cancellation,
  chat replies, summaries, prescriptions and order transitions all create one.
